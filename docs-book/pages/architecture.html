系统架构总览

分层架构、技术栈，一条数据如何流经整个系统。

阅读约 14 分钟 第 4 / 27 篇 源自 docs/ARCHITECTURE.md

分层架构

codex-chat-mobile 采用三层架构：浏览器 → Node 网关 → Codex app-server。每层职责清晰，不越界。

各层职责

表现层（public/index.html + public/js/app.js）

  • public/index.html 提供 HTML/CSS shell，public/js/app.js 作为外部 ESM 承载应用交互
  • 渲染：文本增量、reasoning、命令/工具卡片、文件变更、审批
  • 交互：输入框、审批按钮、斜杠命令、附件上传
  • 状态：连接状态、会话状态、实例切换

网关层（server.js）

  • HTTP 路由：静态资源、健康检查、VAPID 公钥
  • Socket.IO 事件：鉴权、路由、ack 统一格式
  • 实例生命周期：agents map 按 instanceId 维护活跃会话
  • 设备信任：新设备需已信任设备批准
  • Web Push：VAPID 推送通知

桥接层（agent-appserver.js）

  • JSON-RPC 2.0：请求 ID 管理、超时、重试
  • 生命周期：initialize → thread → turn
  • 事件映射：app-server 通知 → agent:event 信封
  • 审批代理：ApprovalBroker 分类与决议
  • 队列：输入队列、中断、steer

执行层（codex app-server）

  • AI 对话：模型调用、流式响应
  • 工具执行：命令运行、文件操作
  • 审批请求：命令/文件/权限审批

组件 技术 版本 用途
运行时 Node.js ≥ 20 ESM、原生 test runner
HTTP 框架 Express 5 路由、中间件、静态托管
实时通信 Socket.IO 4.x 双向事件、ack、命名空间
协议 JSON-RPC 2.0 — 连接 Codex app-server
传输 stdio NDJSON — 长驻子进程通信
推送 Web Push (VAPID) — 审批通知
测试 node:test + Playwright — 单元/集成/E2E

关键数据流

四条主链路：

1. 发消息

sequenceDiagram participant B as 浏览器 participant S as server.js participant A as agent-appserver.js participant C as codex app-server B->>S: user:message {text} S->>A: turn/start (或 turn/steer) A->>C: JSON-RPC request C-->>A: item/started → deltas → item/completed A-->>S: agent:event 信封 S-->>B: Socket.IO 广播

2. 审批

sequenceDiagram participant C as codex app-server participant A as agent-appserver.js participant B as 浏览器 C->>A: S→C 审批请求 A->>A: ApprovalBroker 分类 A->>B: approval_request 信封 B->>A: user:approval {decision} A->>C: JSON-RPC response

3. 断线恢复

sequenceDiagram participant B as 浏览器 participant S as server.js B->>S: catch-up {lastSeq} S->>S: 从重放缓冲增量补发 S-->>B: 补发错过的事件

4. 文件上传

sequenceDiagram participant B as 浏览器 participant S as server.js participant A as agent-appserver.js B->>S: user:message {attachments} S->>S: 校验 + owner-only 落盘 S->>A: turn/start (注入路径)

安全边界

安全原则
  • 无托管后端：浏览器直连本机，不经过任何云服务
  • AUTH_TOKEN 为空 → loopback-only：任何非本机部署必须设置 token
  • 审批不自动决议：安全默认，不自动批准也不自动拒绝
  • owner-only 权限：上传文件、审计日志、设备信任都只保存在本机

协议边界

产品依赖 codex app-server，不依赖旧的 codex exec --json 行为。稳定主链路是：

  1. initialize（握手）
  2. initialized（确认）
  3. thread/start 或 thread/resume 或 thread/fork
  4. turn/start 或 turn/steer
  5. 服务端流式通知
  6. turn/completed 或 error 或中断处理

未知 server request 作为协议事件处理，不能静默卡住应用。未知 item type 降级为可见的 raw envelope，而不是直接丢失。
