宽容策略

codex-chat-mobile 的协议设计遵循宽容策略：对未知类型降级而非丢弃，对未处理通知安全忽略。

核心原则
未知 item → raw envelope：不识别的 item type 降级为可见的 raw_item 信封
未处理通知 → 安全忽略：default 分支不报错
审批不自动决议：安全默认，不自动批准也不自动拒绝

降级兜底

未知 item type

当 app-server 发来前端不认识的 item type 时：

graph LR A[app-server 通知] --> B{识别 item type?} B -->|是| C[正常渲染] B -->|否| D[降级为 raw_item 信封]

代码位置：agent-appserver.js 的 handleNotification default 分支。

未知 server request

当 app-server 发来不认识的 S→C 请求时：

  • 回应 -32601 "Unsupported server request"
  • 发送 system 信封通知前端
  • 不静默卡住应用

未处理通知

当 app-server 发来不认识的 S→C 通知时：

  • default 分支安全忽略
  • 不报错、不阻塞
  • RPC 日志记录

未知容错

前端容错

前端对未知类型保持宽容：

  • 未知 item type → 显示 raw_item 信封
  • 未知信封 type → 忽略
  • 未知字段 → 忽略

后端容错

后端对未知类型保持宽容：

  • 未知 Socket.IO 事件 → 忽略
  • 未知 payload 字段 → 忽略
  • 未知 app-server 通知 → 安全忽略

设计权衡

为什么不用 WebSocket 直连 app-server？

原因
codex app-server 的 --listen ws:// 是 experimental/unsupported，且带 Origin 头一律 403。浏览器无法直连 app-server，必须经本项目 Node 网关。

为什么用 stdio 而不是 HTTP？

  • 零网络配置：不需要开放端口
  • 子进程隔离：每个实例独立进程
  • 简单可靠：标准输入输出，无网络复杂性

为什么审批不自动决议？

  • 安全默认：不自动批准（可能执行危险操作）
  • 不自动拒绝：可能阻塞正常工作流
  • 用户控制：必须显式批准或拒绝

错误处理

背压重试

当 app-server 返回 -32001 "Server overloaded" 时：

graph LR A[发送请求] --> B[收到 -32001] B --> C[指数退避] C --> D[重试] D --> E{成功?} E -->|是| F[继续] E -->|否| G[达到上限?] G -->|否| C G -->|是| H[报错]

进程崩溃恢复

当 app-server 子进程崩溃时：

  1. 标记实例状态
  2. 清理 pending 队列
  3. 重启子进程
  4. thread/resume 续接

断线恢复

当浏览器断线重连时：

  1. 发送 catch-up 带最后 seq
  2. 从环形重放缓冲增量补发
  3. 避免重复近期消息
