从 exec 到 app-server

codex-chat-mobile 的协议模型经历了重大转变：从旧的 codex exec --json 方案迁移到长驻 codex app-server 子进程。

核心变化
旧方案：每次对话启动一个 codex exec 进程，单次交互
新方案：长驻 codex app-server 子进程，JSON-RPC 2.0 over stdio

为什么切换

维度 codex exec --json codex app-server
进程模型 每次对话启动新进程 长驻子进程
协议 自定义 JSON 流 JSON-RPC 2.0
会话持久化 无 thread JSONL
审批 有限支持 完整 S→C 请求
流式响应 基础 原生 item/delta
多会话 不支持 thread/start, resume, fork

app-server 协议模型

握手

sequenceDiagram participant C as Client (codex-chat-mobile) participant S as Server (codex app-server) C->>S: initialize {clientInfo, capabilities} S-->>C: result {serverInfo} S-->>C: initialized (notification)

线程生命周期

stateDiagram-v2 [*] --> Created: thread/start Created --> Active: turn/start Active --> Active: turn/steer Active --> Completed: turn/completed Completed --> Active: thread/resume Completed --> Forked: thread/fork Completed --> Archived: thread/archive Archived --> Active: thread/unarchive Completed --> Deleted: thread/delete

Turn 生命周期

sequenceDiagram participant C as Client participant S as Server C->>S: turn/start {input, model, cwd} S-->>C: turn/started (notification) loop 流式响应 S-->>C: item/started S-->>C: item/agentMessage/delta S-->>C: item/completed end S-->>C: turn/completed {status}

审批模型

审批是 S→C（Server to Client）请求，必须应答，否则 turn 挂起：

sequenceDiagram participant S as Server participant C as Client S->>C: item/commandExecution/requestApproval Note right of S: turn 挂起等待 C->>S: {decision: "approve"} Note left of S: turn 继续执行

支持的审批类型：

  • item/commandExecution/requestApproval — 命令执行
  • item/fileChange/requestApproval — 文件变更
  • item/permissions/requestApproval — 权限请求
  • item/tool/requestUserInput — 用户输入

通知流

app-server 通知是单向的 S→C 消息，不需要应答：

通知 用途
item/started item 开始
item/agentMessage/delta 文本增量
item/reasoning/textDelta 推理增量
item/commandExecution/outputDelta 命令输出增量
item/completed item 完成
turn/completed turn 完成
thread/archived 线程归档

三层集合模型

同一批方法在不同视角下可见性不同：

graph TB A[官方文档层
developers.openai.com] --> B1[默认导出层
generate-ts] A --> B2[全量 schema
generate-ts --experimental] B1 --> B2
  • A：官方文档层
  • B1：默认导出层，稳定 API 面（.protocol/stable/）
  • B2：全量 schema，含 experimental

generate-ts（不带 --experimental）默认过滤全部 #[experimental] 门控的请求方法，但不过滤通知。因此会出现「看得到 realtime/remoteControl/process 的通知、却看不到对应请求方法」的现象。

实验门控

B2∖B1 的方法需要 feature flag 隔离：

分组 方法 本项目现状
网页终端 command/exec + write|resize|terminate 用 PTY 系列承载
历史分页/搜索 thread/turns/list、thread/search 降级到 thread/read
实时语音 thread/realtime/* 仅跟踪通知
远程控制 remoteControl/* 仅跟踪通知

使用实验功能需设置 CODEX_P3_EXPERIMENTAL=1 并在 initialize 声明 experimentalApi: true。
