演进主线

codex-chat-mobile 的架构演进经历了三个阶段：从原型到生产，从单一会话到多实例，从本地到可远程访问。

阶段一：原型验证

时间线
项目初期，核心目标是验证「在手机上控制 Codex CLI」的可行性。

关键决策：

  • 选择 app-server 模式：放弃旧的 codex exec --json，采用长驻 codex app-server 子进程
  • stdio JSON-RPC：通过标准输入输出通信，避免网络协议复杂性
  • 初始单文件前端：原型阶段由 public/index.html 独立承载前端；当前已拆为 HTML/CSS shell 与外部应用模块

技术选型理由：

选择 理由
Node.js 与 Codex CLI 同生态，ESM 原生支持
Socket.IO 双向事件、ack、自动重连、命名空间
Express 5 轻量、成熟、中间件生态
stdio JSON-RPC 零网络配置、子进程隔离

阶段二：功能完善

原型验证成功后，进入功能完善阶段：

审批系统

  • ApprovalBroker：按 method 精确分类（command/file/permission/userInput）
  • 撤销支持：监听 serverRequest/resolved 撤销他端已决弹窗
  • Web Push：审批到达时推送通知（需 HTTPS + VAPID）

多实例

  • agents map：按 instanceId 维护活跃会话
  • 标签隔离：一条 turn 的流不会串到另一个标签
  • 工作区路由：WORK_DIR + WORK_DIRS 白名单

断线恢复

  • catch-up：客户端重连后发 catch-up 带最后 seq
  • 重放缓冲：环形缓冲区增量补发，避免重复近期消息
  • 进程崩溃恢复：标记实例、重启并 thread/resume 续接

阶段三：安全加固

功能稳定后，进入安全加固阶段：

鉴权体系

  • AUTH_TOKEN：空 → loopback-only；非空 → timing-safe 比较
  • 设备信任：新设备需已信任设备批准
  • Admin 门控：ENABLE ADMIN 解锁 + 逐操作确认 + owner-only 审计

文件安全

  • 上传校验：类型、大小、数量限制
  • owner-only 落盘：writeOwnerOnlyFile
  • symlink 防御：防止符号链接攻击

日志脱敏

  • 路径脱敏：sanitizePath
  • token 脱敏：maskToken
  • 敏感字段过滤：RPC 日志中的 token/secret/password 等

阶段四：协议标准化

随着 Codex CLI 的演进，协议层逐步标准化：

协议基线

  • .protocol/stable/：pin 住的协议基线，由 generate-ts 导出
  • protocol:check：检查覆盖与漂移
  • 版本锁定：.codex-version 文件

三层集合模型

graph TB A[官方文档层] --> B1[默认导出层] A --> B2[全量 schema] B1 --> B2
  • A：官方文档层（developers.openai.com）
  • B1：默认导出层（generate-ts，稳定 API 面）
  • B2：全量 schema（含 experimental）

产品主干只用 A∩B1；B2∖B1 一律 feature flag 隔离。

关键里程碑

里程碑 标志
原型验证 能在手机上发消息并看到流式响应
审批可用 在手机上批准/拒绝命令执行
多实例 多个标签隔离活跃对话
断线恢复 刷新页面后不丢消息
安全加固 AUTH_TOKEN + 设备信任 + Admin 门控
协议标准化 protocol:check 通过
文档完善 完整中文文档 + AGPL-3.0
